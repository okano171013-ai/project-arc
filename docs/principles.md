# Principles

Project ARCの設計・実装における判断基準。迷ったときは
ここに立ち返る。各ADR（Architecture Decision Record）は、
どのPrincipleに基づく判断かを明記すること。

さらに上位の文書として[`docs/constitution.md`](./constitution.md)
（ARC Constitution、7条文）がある。Principle同士、あるいは
Principleと条文が衝突するように見える場合は、まず`constitution.md`
の「条文間の関係」を確認する（特に第6条とPrinciple 3・6の関係）。

---

### Principle 1｜人間が最終意思決定者である

AI（ARC / Gemini / Claude Code）はいかなる判断も
確定させない。3AIの役割は判断材料・提案・実装の提供に
限定され、最終決定権は常に人間（Owner）に残る。

### Principle 2｜AIは判断材料を提供する存在である

AIの出力は「答え」ではなく「材料」として扱う。
特に、確信度の低い情報や解釈を断定的に提示しない
（Principle 5と直結）。

### Principle 3｜継続性を最優先する

一時的に高機能であることよりも、3ヶ月後・1年後も
無理なく続けられることを優先する。習慣化を壊す複雑さは
機能価値より優先度が低い。

### Principle 4｜記録は資産である

日々の記録（学習・健康・支出・振り返り）は、後から
検索・分析・振り返りに使える形で蓄積する。使い捨ての
ログにしない。データ構造を変更する際は、過去データの
移行可能性を必ず考慮する。

### Principle 5｜推測は推測として扱う

AIが生成した分析・要約・示唆のうち、事実に基づかない
推測部分は、事実と明確に区別して提示する。特にARCの
意思決定支援においては、この区別が意思決定の質に
直結するため厳格に扱う。

### Principle 6｜UXを最優先する

技術的に優れていても、日々使う上での摩擦が大きい設計は
採用しない。「毎朝・毎晩、無理なく触れるか」を実装前に
必ず検証する。

（`docs/constitution.md`第6条「マネジメントは遠慮しない」との
関係：本Principleは操作性・UXの基準、第6条はARCの発言内容・姿勢の
基準であり、適用範囲が異なる。詳細はconstitution.md参照）

### Principle 7｜機能追加より意思決定支援を優先する

新機能を追加する際、「便利そうだから」ではなく
「今日の判断の質を上げるか」を基準に取捨選択する
（Vision: Core Missionに直結）。

### Principle 8｜長期保守性を重視する

Project ARCは1〜2ヶ月で終わるプロジェクトではない。
Clean Architecture・SOLID原則・テスト容易性など、
将来の自分（またはClaude Code）が安全に変更を加えられる
構造を優先する。

### Principle 9｜段階的拡張（Incremental Scope）

一度に全てを作らない。Version1で土台を固め、必要性が
明確になった時点で機能・抽象化を追加する（YAGNI）。
先取りした抽象化・依存関係の追加は、具体的な必要性が
確認できるまで見送る。

### Principle 10｜責務は交換可能ではなく分担する

人間・ARC・Gemini・Claude Code・Project ARC自体、それぞれの
責務境界を越えない。ある処理を「誰でもできるからどれかに
やらせる」のではなく、「その処理は本来誰の責務か」を
基準に設計する（docs/ai-roles.md参照）。

---

## 優先順位の衝突が起きたときの扱い

Principle同士が衝突する場合（例：UX最優先 vs 長期保守性）は、
上から順に優先度が高いとみなす。ただしこれは目安であり、
最終判断はPrinciple 1に基づき人間が行う。
