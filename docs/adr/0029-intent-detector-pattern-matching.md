# ADR 0029: IntentDetectorの機械的パターンマッチング設計

## ステータス

承認済み

## 関連Principle

- ADR 0022（CandidateBuilderの機械的パターンマッチング設計）
- ARC Constitution 第2条（Systemは判断しない）

## コンテキスト

Version13指示書3章は、質問をRetrieval/Decision/Noneへ分類する
Intent Detectionを求めていた。同時に「AIによる自然言語理解は
使わない。Version12同様ルールベースでよい」と明記していた。

指示書が挙げた3例（「前に読んだ論文」→Retrieval、「今日は行政法と
民訴法どっち？」→Decision、「こんにちは」→None）は、日本語の
表層的な語彙・記号（過去を示す語、選択を示す語、疑問符の有無）で
ある程度区別可能だが、実機確認で使う「この参考書買う？」のような
Yes/No型の質問をどちらに分類するかが設計上の論点だった。

## 決定

`IntentDetector`は以下の優先順の固定パターンによる機械的分岐のみで
構成する。

1. 質問文に過去の記録を示す語（「前に」「以前」「読んだ」「保存
   した」等）が含まれる → `Retrieval`
2. 質問文に選択・決定を示す語（「べき」「どちら」「どっち」「何を」
   等、Version12のCandidateBuilderがトリガーとして使う語と同じ
   語彙、ADR 0022）が含まれる、または文末が疑問符で終わる →
   `Decision`
3. 上記のいずれでもない → `None`

`conversation`（直近の会話文脈）引数は、Intent判定には使わない。
判定は`question`（直近の質問）のみを見る。

## 根拠

DECISION_MARKERSをCandidateBuilder（ADR 0022）のトリガー語彙と
意図的に揃えたのは、IntentDetectorが`Decision`と判定した質問は
その後`DecisionEngineUseCase`（内部でCandidateBuilderを呼ぶ）へ
そのまま渡されるため——両者の語彙が食い違うと、「Decisionと判定
したのにCandidateBuilderが候補を1つも作れない」という不整合が
起きうる。同じ語彙を共有することで、この2段階の判定が一貫した
結果を生む。

「文末が疑問符で終わる」場合をDecisionのフォールバックにしたのは、
日本語の「〜？」で終わる問いの多くが実質的にYes/No型または選択を
求める意思決定質問である、という表層的な観察に基づく（「この
参考書買う？」等）。これは意味理解ではなく、句読点という機械的に
検出可能な記号への依存であり、Constitution第2条が禁じる「意味を
理解した上での判断」には該当しない。

`conversation`引数をIntent判定に使わない判断は、直近1件の質問文
だけを見る方が、複数ターンの会話履歴を解析するより遥かに単純で
説明可能だからである。会話履歴の文脈を踏まえた判定は、パターン
一致では対応しきれない領域（真の自然言語理解）に踏み込むリスクが
高く、指示書16章の「自動推論」禁止に抵触しかねない。

## 影響

- RETRIEVAL_MARKERS/DECISION_MARKERSに含まれない語彙で書かれた
  質問は、文末の疑問符の有無でDecision/Noneのいずれかに機械的に
  振り分けられる。誤判定（例：疑問符付きの雑談を Decisionと誤認）
  が起きても、`DecisionEngineUseCase`は根拠が見つからなければ
  `missingInfo`を返すだけであり、実害（誤った書き込み等）は
  発生しない設計になっている。
- `conversation`引数はAPIの入力として受け付けるが、現時点では
  未使用（呼び出し側の記録用に受け取るのみ）。将来Intent判定を
  会話履歴で補強する場合は、この決定の見直しとADRの改定が必要。
