# ADR 0022: CandidateBuilderの機械的パターンマッチング設計

## ステータス

承認済み

## 関連Principle

- ARC Constitution 第2条（Systemは判断しない）
- `docs/ai-roles.md` Principle 5（存在しない情報を捏造しない）

## コンテキスト

Version12指示書3章は、質問文から「考えられる選択肢」を生成する
CandidateBuilderを求めていた（例：「今日は何を勉強するべき？」→
「行政法」「民訴法」「会社法」）。同時に指示書16章はAI API呼び出しを
明示的に禁止しており、自然言語理解を伴う候補生成はできない。

「AとBどちら」のような明示的な二択、「何を〜べきか」のような開放的な
選択質問、「〜べきか？」のような二値の意思決定質問は、日本語の
表層パターンとしては異なる形をしているが、これらを区別してそれぞれ
に妥当な候補を出すには何らかの分岐ロジックが要る。

## 決定

`CandidateBuilder`は、以下の優先順の固定パターンによる機械的分岐
のみで構成する。意味理解・AIは一切用いない。

1. 呼び出し側（Owner/ARC）が`candidates`を明示していれば、それを
   そのまま使う（最優先）。
2. 質問文に既存ExternalKnowledgeのtopicが2つ以上、部分文字列として
   含まれる場合、それらを候補にする（例：「行政法と民訴法どちら」）。
3. 質問文に「何を」「どれ」等の選択を促す語が含まれる場合、既存の
   全topicを候補として提示する（意味的な関連は判定しない、単に
   Ownerが選べる材料をそのまま並べる）。
4. topicが1つだけ質問文に含まれる場合は、それと「その他」を候補に
   する。
5. 上記のいずれでもなければ、Yes/No型の質問とみなし
   `["実行する", "実行しない"]`を返す。

## 根拠

この設計は、Version6の`RuleBasedCaptureClassifier`（固定キーワード
表による下書き提案、断定しない）と同種の思想を踏襲している——
「Systemが理解して判断する」のではなく、「機械的なパターン一致で
材料を提示するだけ」という一貫した境界線。

各分岐は決定的で説明可能であり、「なぜこの候補が出たか」を
コード上のルールから常に説明できる。これは、AIによる候補生成が
持つ「なぜその候補が選ばれたか説明できない」という性質とは対照的
であり、Constitution第2条の「Systemが暴走しない」という要件と
整合する。

明示的な`candidates`指定を最優先にしたのは、この機械的分岐が
拾えない質問（複雑な言い回し、topicとして登録されていない選択肢等）
に対して、Owner/ARC自身が候補を明示できる逃げ道を用意するため。
これにより、パターンマッチングの限界がそのままシステムの限界には
ならない。

## 影響

- 質問文にExternalKnowledgeのtopicとして登録されていない語句が
  含まれる場合（例：「この参考書を買うべき？」で「参考書」という
  topicが存在しない場合）、機械的分岐はYes/No型にフォールバック
  する。これは意図した挙動だが、Ownerから見ると「候補が具体的で
  ない」と感じられる可能性がある——その場合は`candidates`を明示
  して呼び出すことを推奨する（次Versionの改善候補としてReportに
  記録）。
- 質問文の言い回しに依存するため、同じ意図の質問でも表現が変われば
  異なる候補が出ることがある（自然言語理解ではなく文字列パターン
  一致であるため、これは設計上の制約として許容する）。
